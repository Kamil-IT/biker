# React + TypeScript + Vite

This template provides a minimal setup to get React working in Vite with HMR and some ESLint rules.

## Application overview

**Addresses (URL routing).** Every view has its own address, so a shared link, a new tab, F5 and Back/Forward show the same thing (not SEO — the app is still a client-rendered SPA):

| Address | View |
|---------|------|
| `/` | home — search form (empty) + "Najpopularniejsze rowery" |
| `/search?q=…&brand=…&model=…&year=…&wheel_size=…&frame_size=…&bike_type=…&is_electric=…` | search results; the names are the API fields (free text = `q`), always in that order (`src/searchQuery.ts`); `/search` without a usable parameter → `/` |
| `/bike/{bike_id}` | bike details (numeric `bike.id`); unknown or malformed id → "Nie znaleziono roweru" + a link to the search, the address is kept |
| `/equipment/{equipment_id}` | equipment view (numeric `equipment.id`); unknown → "Nie znaleziono wyposażenia" |
| `/bike-for-your-fit` | "Rower na Twoją miarę" (the old `/rower-na-twoja-miare` is rewritten to it) |
| `/contact` | "Kontakt" (the old `/kontakt` is rewritten to it) |

There is no router library: `hooks/useRoute.ts` maps `location` to a `Route` (`home` / `search` / `bike` / `equipment` / `fit` / `contact`), rewrites a non-canonical address with `replaceState` (trailing slash, old paths, unknown → `/`, search parameters normalised), pushes an entry per navigation, and listens to `popstate`. Each history entry's state holds `from` (the in-app address it was opened from — the "Wróć" buttons go **back** through the history when that is their parent view, else push the parent's address) and `scrollY` (restored instantly on Back/Forward; `history.scrollRestoration = 'manual'`). `App.tsx` decides the view from the route and loads what the address needs in one effect: `/search?…` runs its search at once (no `/v1/bike/parse` step) and fills the form and filters panel, unless the same query's results are already in memory — so Back from a bike shows the same results, at the same scroll position, without a request; `/bike/{id}` reads `POST /v1/bike/by-id` unless that bike is the one in memory; `/equipment/{id}` opens the item unless it is already shown. The address changes only when a search actually runs (the second submit after a parse, not the parse), and each search is a new history entry. `document.title` follows the view: `Trek Marlin 5 — Biker`, `<equipment name> — Biker`, `Wyniki wyszukiwania — Biker`. nginx's SPA fallback (`try_files … /index.html`) and Vite already serve `index.html` for every path, and the build's asset URLs are absolute, so nested paths load. Result and popular cards are real `<a href="/bike/{id}">` links (`ResultCard` `href`), so a modified or middle click opens a new browser tab.

**Top tabs (TODO-041).** Under the BIKER wordmark the header carries a tab row (`components/TopTabs.tsx`): **Szukanie rowerów** (→ the last search's address, else `/`; active on `/`, `/search`, `/bike/…`, `/equipment/…`), **Rower na Twoją miarę** `/bike-for-your-fit`, **Kontakt** `/contact`. The tabs are plain `<a href>` links (a modified or middle click opens a new browser tab) with `aria-current="page"` and a terracotta bar on the active one. The search state stays in memory inside `App`, so leaving for another tab and coming back keeps the results; the BIKER wordmark and "Nowe wyszukiwanie" reset the search and return to `/`. `components/FitComingSoonPage.tsx` is a "Wkrótce" teaser for the AI bike fitter (SVG sketch with a `.scan` sweep from `index.css`, hidden under `prefers-reduced-motion`); `components/ContactPage.tsx` is a contact form shown **disabled** with a "wkrótce" notice — there is no contact backend, nothing is sent. Approved mockups: `docs/mockups/zakladki/`.

The search views live in `components/SearchPage.tsx` (hero + form, popular list on `/`, results on `/search`), the bike details state and calls in `hooks/useBikeDetails.ts`, the equipment ones in `hooks/useEquipment.ts`; `components/NotFoundPage.tsx` is the "Nie znaleziono …" page.

**UI language: Polish.** Every user-visible string (labels, buttons, placeholders, `aria-label`s, error messages, `index.html` title/description, `lang="pl"`) is Polish, hard-coded in the components (no i18n library). Filter `<select>`s keep their **English `value`s** — only the `label` is translated (`SearchInput.tsx` `Option { value, label }`), because the backend matches those values against its English data. Content returned by the backend (explanations, reviews, spec **values**, component names) is shown as-is — except the spec-tree **labels**: category, subcategory and spec-key names are translated at display time by `src/specLabels.ts` `translateLabel()` (case-insensitive dictionary, plus `Front …` / `Rear …` / `Max …` prefixes and a trailing `(…)` qualifier such as `Weight (Size M)` → `Waga (rozmiar M)`; unknown labels fall back to the English original). `CategorySection` in `BikeDetailsShared.tsx` applies it, so it covers both the bike and equipment views; the element-name link still passes the untranslated name to the equipment view. The English UI names below (e.g. "Request data") are the pre-translation names used in task files; on screen they read "Poproś o dane", "Nie mamy jeszcze tych danych", "Zgłoszono ✓", "Szukam na OLX…", "Szukam na Allegro…", "Szukam w Decathlonie…", "Szukam zdjęć…", "Szukam recenzji…", "Szukam danych roweru…", "Szukam danych wyposażenia…", "Nie znaleziono ofert", "Nie znaleziono zdjęć", "Nie znaleziono recenzji", "Nie znaleziono danych", "Nie znaleziono", "Czytaj recenzję", "Źródła", "Używane" / "Nowe"; on the home page "Najpopularniejsze rowery", "Ocena eksperta", "Brak oceny".

The numeral is the rating ("8.4" over "/ 10"), **"—"** while the answer is pending and **"?"** when the bike has no stored review (or the call failed); the bar reads "Ocena eksperta" ("Ocena eksperta…" / "Brak oceny") and fills to `rating × 10 %`. Cards keep the backend order until every rating has settled, then the list is sorted by rating descending with unrated bikes last (stable). **Explanation and chips (TODO-041):** the card's paragraph is the bike's stored short description and its chips are drivetrain / brakes / frame-material names computed by the backend from stored components; `ResultCard` renders each **only when non-empty**, so a bike without stored details (typical for an AI-found bike) shows neither. There is no "Najlepsze dopasowanie" badge, no percentage and no "Dopasowanie" block in the details header any more. `bikeKey` / `PENDING_RATING` / `NO_RATING` are shared in `src/ratings.ts`.
  **Free text → filters:** a submit with free text and no filters set first calls `POST /v1/bike/parse` and fills the Filters panel from the result, then waits for a second submit. `App.tsx` keeps the parsed text in a `parsedQueryRef`, so **any later submit whose search text differs from it clears every filter first** (`EMPTY_FILTERS`, manual ones included), sends only `{ search }` and parses the new text — typing a different bike can never search with the previous bike's brand/model still in the panel. A submit with the text unchanged does not parse again; it searches with whatever the filters hold, so a filter tweaked by hand still applies. Resetting the app ("BIKER" in the header, "new search" in the results) clears that memory as well, so the same text parses again after a reset.

The automatic `POST /v1/bike/used/olx` on opening the details view is unchanged (it is now a fast DB read on the backend). Every other `RequestDataButton` usage (no `onRequested`) keeps the TODO-027 behaviour.

The equipment view's review (`/v1/equipment/review`) is asked for by its own button (see below).
- **Equipment details** (`/equipment/{id}`, `EquipmentDetailsView`, TODO-042) — the gear counterpart: category eyebrow, the item's name, photo gallery, overview, expert review, and a component spec tree. **No offers/buy links** — equipment is informational only.

A link, a new tab or F5 enters the same address directly.
  **Stored data + automatic details search:** all equipment state and calls live in `hooks/useEquipment.ts` (`enter(id, fromBikeId)` per entry; the item already shown stays as it is unless its last read or search failed). Opening sends three fast DB reads by id: `POST /v1/equipment/by-id` (name, category, the first bike linking the item), `POST /v1/equipment/details` and `POST /v1/equipment/photos` (`{ equipment_id }`). When the details read is empty (no description text **and** no components — the item has no details stored), the details search `POST /v1/equipment/details/search` `{ equipment_id, bike_id? }` starts **automatically** (`bike_id` = the bike the view was opened from, read from the history entry's `from`; without it the backend takes the first bike linking the item). The **Opis** and **Specyfikacja** slots watch that one run (`detailsRun`, `RequestDataButton` `watch`, "Szukam danych wyposażenia…"); its answer fills both. The searcher stores "Opis niedostępny dla tego produktu." when it finds nothing, so the item never searches itself again — the description slot shows that text and the spec slot a plain "Brak specyfikacji dla tego produktu." note (no button). A failed run (404 / 503 / 502 / 400 subscription limit / network) stores nothing: both slots become a clickable **Poproś o dane** (no `missingType` — equipment has no `/v1/bike/missing` counter), and the next entry of the address searches again.
  **Buttons:** the gallery's **Poproś o dane** (`pendingLabel="Szukam zdjęć…"`, `emptyLabel="Nie znaleziono zdjęć"`) calls `POST /v1/equipment/photos/search` `{ equipment_id, bike_id? }`; the review section's (`"Szukam recenzji…"` / `"Nie znaleziono recenzji"`) calls `POST /v1/equipment/review` `{ company: "", model: <name> }` — the review is no longer fetched on open. Answers that land after another item was opened are dropped.
  **Back:** "Wróć do roweru" goes back to the bike the view was opened from (history Back when that bike is the previous entry), or — for a link / new tab / F5 — to the first bike linking the item (`by-id` `bike`); "Wróć" → home when no bike links it.

`BikeDetailsView` and `EquipmentDetailsView` share their building blocks (`PhotoGallery`, `DescriptionCard`, `ReviewSection`, `LoadingSkeleton`, `CategorySection`) from `components/BikeDetailsShared.tsx`. The overview renders its sources as **citation footnote chips** (`components/CitationChips.tsx`) — a "Sources" row of terracotta pill links showing each source's domain, opening in a new tab with the full URL as a hover tooltip. The expert review renders its sources as a **full-width source table** below the explanation instead: one row per URL, `stars | domain | "Read review →"`, each row an external link with the full URL as a hover tooltip. The stars are decorative, mapped 0–10 → 1–5 from the aggregate `rating` where one exists.

### Docker

`frontend/Dockerfile` builds the bundle (node 24) and serves it from nginx. `nginx.conf.template` is rendered by the image's
envsubst entrypoint at start (only `PORT` and `BACKEND_URL` are substituted, `NGINX_ENVSUBST_FILTER`): SPA fallback plus
`/v1/*` proxied to `BACKEND_URL` — the same routing Vite does in dev. The Dockerfile defaults (`PORT=8080`,
`BACKEND_URL=http://backend:8000`) serve the root `docker-compose.yml`; on Cloud Run `scripts/deploy.ps1` sets `BACKEND_URL`
to the backend service's https URL. The proxy sends the backend's own hostname as `Host` (Cloud Run routes by it) with SNI
on, and keeps the 600 s read timeout for the on-demand searches (`/v1/bike/details/search` and the other `*/search` routes).

### API integration (all proxied via Vite `/v1` → backend on :8000)

| Call | Request | Response |
|------|---------|----------|
| `POST /v1/bike/search` | `SearchPayload` | `{ search, bikes[] }` — each bike with its `id` (the `/bike/{id}` link) |
| `POST /v1/bike/by-id` | `{ bike_id }` | `Bike` `{ id, brand, model, accessories, explanation }` — what `/bike/{id}` opens when the bike is not in memory (link, new tab, F5); 404 → "Nie znaleziono roweru" |
| `GET /v1/bike/popular` | — | `PopularBikesResponse` `{ bikes: [{ id, brand, model, description }] }` — the curated home-page list, already ordered (DB read, no AI, TODO-034); fetched once on app load by `usePopularBikes`; `{ bikes: [] }`, a non-OK answer or a network error just hides the section |
| `POST /v1/bike/details` | `{ company, model }` | `BikeDetailsResponse` (overview + component tree + `short_description` — no photos) — the stored details, a fast DB read (TODO-041); nothing stored → empty description text, `components: []`, `short_description: ""`, shown as the Opis / Komponenty "Request data" buttons |
| `POST /v1/bike/details/search` | `{ company, model }` | `BikeDetailsResponse` — on-demand details search via the searcher service (TODO-041), triggered only by the Opis / Komponenty "Request data" buttons (one shared run fills both); empty result = "Nie znaleziono danych"; 404 when the bike is unknown, 503 when the searcher is not configured/reachable/busy, 502 when it fails |
| `POST /v1/bike/photos` | `{ company, model }` | `BikePhotosResponse` `{ photos }` — stored photo URLs in display order (DB read, no AI), sent on opening the details view; `{ photos: [] }` until the on-demand search below has run |
| `POST /v1/bike/review` | `{ company, model }` | `BikeReviewResponse` — the stored review, a fast DB read (TODO-037); nothing stored → `{ score: 0, explanation: "", ref: [], rating: 0, sources_used: 0 }`, shown as the Review section's "Request data" button. | `POST /v1/bike/allegro` | `{ company, model }` | `BikeOfferResponse` `{ offers, info }` — stored allegro.pl offers only (DB read, no AI, TODO-033; `photos` is always `[]` — the Allegro search stores none); empty until the on-demand search below has run |

| `POST /v1/bike/missing` | `MissingDataRequest` `{ company, model, missing_type }` | `MissingDataResponse` `{ bike_id, missing_type, counter }` (sent by `RequestDataButton`) |
| `POST /v1/bike/used/search` | `{ company, model }` | `UsedBikeResponse` `{ offers, info }` — on-demand OLX search via the searcher service (TODO-031), triggered only by the Used card's "Request data" button; 503 when the searcher is not configured/reachable/busy, 502 when it fails |
| `POST /v1/bike/decathlon/search` | `{ company, model }` | `BikeOfferResponse` `{ offers, info }` — on-demand Decathlon search via the same searcher service (TODO-032), triggered only by the New card's "Poszukaj w Decathlonie" button; a non-Decathlon brand answers 200 with `offers: []` and a Polish `info` at once (no searcher call); 404 when the bike is unknown, 503 when the searcher is not configured/reachable/busy, 502 when it fails |

| `POST /v1/bike/photos/search` | `{ company, model }` | `BikePhotosResponse` `{ photos }` — on-demand photo search via the searcher service, triggered only by the gallery's "Request data" button; 404 when the bike is unknown, 503 when the searcher is not configured/reachable/busy, 502 when it fails |
| `POST /v1/bike/review/search` | `{ company, model }` | `BikeReviewResponse` — on-demand review search via the searcher service (TODO-037), triggered only by the Review section's "Request data" button; empty `ref` / `sources_used` 0 = nothing found; 404 when the bike is unknown, 503 when the searcher is not configured/reachable/busy, 502 when it fails |

`BikeReviewResponse` also carries an aggregate `rating` (0–10, weighted across curated review sources) and `sources_used` count; `ReviewSection` does not display the aggregate rating itself — it only derives the source-table stars from `rating`. Equipment reviews carry neither field, so they fall back to `score` for the stars.
| `POST /v1/equipment/resolve` | `{ bike_id, element_name }` | `EquipmentResolveResponse` `{ equipment_id, name, category }` — the element's equipment row, created empty when missing (no AI); sent by a click on an element without `equipment_id` |
| `POST /v1/equipment/by-id` | `{ equipment_id }` | `EquipmentItemResponse` `{ equipment_id, name, category, company, model, bike }` — identity + the first bike linking the item (back target); 404 → "Nie znaleziono wyposażenia" |
| `POST /v1/equipment/details` | `{ equipment_id }` | `EquipmentDetailsResponse` (overview, component tree, `short_description`, `equipment_id` — no photos, no offers) — stored data, a DB read (TODO-042); empty description text and `components: []` = nothing stored → the details search starts by itself |
| `POST /v1/equipment/photos` | `{ equipment_id }` | `EquipmentPhotosResponse` `{ photos, equipment_id }` — stored photo URLs (DB read); `photos: []` until the search below has run |
| `POST /v1/equipment/details/search` | `EquipmentSearchPayload` `{ equipment_id, bike_id? }` | `EquipmentDetailsResponse` — the equipment details search via the searcher, started automatically while nothing is stored (and by the Opis / Specyfikacja button after a failure); "not found" comes back as the stored "Opis niedostępny dla tego produktu."; 404 unknown item / no bike links it, 503 searcher not configured / unreachable / busy, 502 searcher failed, 400 subscription limit |
| `POST /v1/equipment/photos/search` | `EquipmentSearchPayload` | `EquipmentPhotosResponse` — on-demand photo search via the searcher, sent only by the gallery button; same error statuses |
| `POST /v1/equipment/review` | `{ company?, model }` | `EquipmentReviewResponse` (`score`, `explanation`, `ref[]` — review/forum links only) — sent only by the review section's button |

Equipment is entered from a linkable component name in a bike's spec tree (or its `/equipment/{id}` address). `POST /v1/bike/details` elements carry `equipment_id` (`ComponentElement.equipment_id`, null until a click resolved or a search linked them).
